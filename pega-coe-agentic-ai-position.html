01Executive summary

The bank runs one production agent runtime: Agent.CBA. Pega is the process plane around it. The COE's job is to make that split workable for every Pega application in production, without pretending Pega's own agent features do not exist and without letting them into production.

Pega's 2025 and 2026 releases ship a real agent runtime: agent rules (Rule-AI-Agent), tool rules, knowledge tools, agent-to-agent delegation, an MCP server that exposes cases and workflows as tools, an MCP client, A2A connectivity, and prebuilt agents. The features work. The bank's position is still that production agents do not run on them, for three reasons that survive scrutiny: one runtime standard for evaluation and incident response, portability of agent logic and memory out of platform-bound rules, and change velocity for prompts, models, and tools.

That leaves a large, useful role for Pega. Pega owns the case lifecycle, assignments, SLAs, human work, integrations, decision logic, and the audit trail. It also becomes the richest tool surface an agent can call: case reads, case actions, status, documents, and history, exposed through the MCP server under least privilege. Design-time GenAI stays in Pega as well: Blueprint for intake, Autopilot for scaffolding, and the authoring MCP plugins so that coding agents build governed Pega rules inside branch-isolated workspaces with human approval.

The paper's position in five statements:

1

Runtime agents: Agent.CBA only.

Any production component that plans, chooses tools across turns, or holds a goal is built and run in Agent.CBA (Python, Pydantic AI and peer frameworks, Temporal for durable execution, HoneyHive for evaluation and traces). Rule-AI-Agent in production is out of policy.

2

Pega owns process and evidence.

Case lifecycle, assignments, SLAs, human decisions, integrations, decision logic, and the audit trail. This is not a consolation prize; it is the part regulators and auditors ask about first.

3

Pega owns the tool surface agents call.

Agent actions on Pega data and cases run through curated MCP tools backed by Rule-AI-Tool definitions, with confirmation flags, masking, and per-domain least privilege.

4

Design-time agentic AI is encouraged.

Blueprint, Autopilot, and authoring MCP plugins are allowed and should be the default intake and build path, subject to branch isolation, no production data, and human approval of every merged rule.

5

Exceptions are explicit and expiring.

Waivers need a named owner, an expiry date, an exit test, and a register entry. Silence is not approval.

The engineering value of this split is straightforward. Agents get the bank's best case context through a governed tool surface. Pega teams get a repeatable pattern instead of a per-team decision. Risk gets one runtime to assess, one eval pipeline to inspect, and one kind of agent identity to control. The cost is integration work and some lost low-code agent authoring for business users, and that cost is stated plainly in Section 12.

02Scope, assumptions, and how to challenge this paper

Every recommendation in this paper is conditional. If an assumption below is wrong, the affected recommendations are void, and the paper says which ones.

Load-bearing assumptions

  1. Pega stays in the estate for process and decisioning. CBA's Customer Engagement Engine runs on Pega Customer Decision Hub, and Pega remains the case management and workflow platform for the applications in scope29. If Pega is being consolidated away, this paper's role for Pega shrinks to a migration chapter, and the guardrails here become exit guidance instead.
  2. Agent.CBA remains the single approved runtime for production agents, with Python, Pydantic-style typed agents, Temporal durable execution, HoneyHive evaluation and traces, and bank-approved provider SDKs (OpenAI, Google, Anthropic)40. This is an internal brief, not public information. If a second runtime is ever approved, revisit Sections 4, 5, and 8.
  3. Model access runs through a bank-approved gateway. CBA publicly describes a controlled environment of 100+ language models and a GenAI Studio34. Pega's model routes (GenAI Connect, bring-your-own-model) must point at those approved endpoints, never directly at public model APIs.
  4. The regulatory baseline is APRA's April 2026 AI letter and its four observation areas, CPS 230 (in force since 1 July 2026), CPS 234's third-party reach, the OAIC's automated decision-making transparency rules from 10 December 2026, and ASIC's 2026-27 banking AI review4143444547.
  5. Licensing is not free. Pega GenAI Coach is sold as an add-on12, agentic features and MCP entitlements vary by edition and contract, and Infinity '26 introduced a flat fee per resolved case for agentic workflows152. Confirm entitlements with Pega licensing before design, not after.

Scope boundaries

  • In scope: Pega applications in production, their design-time tooling, and their integration with Agent.CBA.
  • In scope: what the COE approves, reviews, and supports.
  • Out of scope: the internal design of Agent.CBA; this paper states the Pega-side contract only. The Agent.CBA team owns its own standards.
  • Out of scope: consumer-facing channels outside Pega (the CommBank app companion and messaging orchestration are separate programmes3239).
How to challenge this paper

Bring one of three things: a capability that Pega does better than Agent.CBA at lower total cost, a production scenario the four standard patterns cannot serve, or a portability mechanism on the Agent.CBA side that changes the lock-in math. Section 12 lists the specific triggers that would make the COE change this position. "Pega can do it too" is not one of them.

03What counts as an agent

Most arguments about "agents in Pega" are really arguments about words. This paper uses four categories, and the policy depends on the category, not the label a vendor or a team applies.

Working taxonomy
CategoryDefinitionExamplesProduction home
Assistive AI Single turn or single task. Produces a draft, summary, classification, or suggestion. A human or a deterministic rule acts next. Case summarization, email drafting, document field extraction, in-UX guidance (GenAI Coach), a mapped LLM response in GenAI Connect. Either plane. In Pega, bounded and validated: see Section 5, Amber rows.
Deterministic automation No model in the decision path. Rules, flows, decision tables, integrations. Case routing, eligibility checks, SLAs, correspondence assembly. Pega. This is the default and should absorb work that teams are tempted to call an agent.
Bounded agent Goal-directed across multiple steps. Chooses tools at runtime. Output validated against a schema before any action. A claims-triage agent that reads a case, calls two tools, and returns a recommendation with evidence. Agent.CBA. Pega exposes the case tools the agent needs (Pattern P1).
Autonomous agent Plans over longer horizons, spawns sub-agents, acts across systems, handles exceptions on its own. A collections agent that negotiates follow-ups over days; a remediation agent that opens and closes child work. Agent.CBA, with Temporal durability and human gates. Never Pega.

Two consequences follow. First, a case step that calls an approved agent service is not itself an agent; it is a service call inside a deterministic flow. It belongs in Pega. Second, a "no-code agent builder" feature does not change the category of what it builds. If it plans, it is a runtime agent, and it does not run in Pega.

04The constraint: why production agents do not run in Pega

The honest version of the lock-in argument, followed by what the bank gives up by holding this line.

The strongest version of the argument for Pega agents

Steel-man it first. Pega's agent runtime is not a toy. An agent rule carries a system prompt, a guardrails prompt, response style, examples, tools, and knowledge sources, all under platform version control27. Agents execute inside the same case context they need, so grounding is native rather than marshalled over an API. Pega ships runtime content filtering across providers, tenant isolation, and audit records for agent conversations12. MCP exposure is first-party, so agents can call governed Pega tools with OAuth out of the box5. On a feature-by-feature basis, Pega's runtime is credible, and a team that builds there will get a working demo quickly.

The argument fails on governance economics and portability, not on features.

Reason 1: one runtime standard beats two

The bank's ability to assure agents depends on repetition: one evaluation system, one trace format, one set of release gates, one incident playbook, one identity model for non-human actors. APRA's April 2026 letter is explicit that boards and second-line functions are already stretched on AI assurance, that security and identity practices "have not yet adjusted to nonhuman actors such as AI agents," and that entities should be able to substitute or exit critical AI providers41. A second agent runtime, even a good one, doubles the assurance surface and creates exactly the concentration and opacity APRA describes. The bank's own public reasoning has pointed the same way since 2023: the AI platform was built to hold 100+ models so that CBA would "not be locked into a specific product provider"36.

Reason 2: agent logic and memory must be portable artifacts

An agent is software. Its prompts, tool wiring, guardrails, model choice, and evaluation datasets should live where the bank can diff them, review them, test them, and move them. In Pega, those artifacts live as rules in a ruleset, executed by Pega's runtime. That is not a defect in Pega; it is the nature of a platform. It does mean that migrating an agent out later is a rewrite plus a re-evaluation, not a deployment change.

Memory sharpens the point. Pega persists agent executions and conversation records in platform-bound classes (Pega-Autopilot-Conversation, instances prefixed PXCONV-, linkable to cases through pyContextID), per Pega staff on the community forum10. Interaction history inside a platform's managed memory is the least portable asset an agent has; one industry survey of large enterprises found that only about a quarter keep most of that record in a neutral schema, and that a model switch costs a median of 21 to 60 engineer-days50. The bank should own the memory layer, not inherit it.

Reason 3: agents change on a software cadence, not a platform cadence

Prompts, tools, model routes, and guardrails change weekly during development and monthly in production. That cycle belongs in the Agent.CBA code pipeline with eval gates, not in a platform release train. Pega rules can be branched and deployed quickly, but the runtime and its certified model catalog still set the pace; Pega itself warns that model availability is gated by provider, region, and certification, and that model changes are locked at runtime in connector rules1314.

What Pega gets right, and what this paper does not dispute

  • Pega's MCP work is genuinely openness-aligned. Exposing cases and workflows as MCP tools is the right direction, because the tool protocol is open and any agent runtime can consume it35.
  • Pega's runtime guardrails are real and auditable. The bank's objection is duplication, not quality12.
  • Pega's own design-time heavy, runtime light position (the "Predictable AI" framing: move reasoning to design time, keep runtime mostly deterministic) is compatible with this paper's split, provided "design time" is read as design-time tooling and "runtime" stays agent-free151.

What the bank gives up by holding the line

Name the costs, because teams will feel them:

  1. Native case-context grounding. Agents will get case context through the MCP tool surface instead of a preloaded data page. That is an integration cost, and Section 6 pattern P1 makes it a solved pattern rather than a per-team project.
  2. Low-code agent authoring for business teams. Business users cannot assemble agent rules in Pega. They will define outcomes and review proposals; engineers write the agent code. That is the bank's chosen operating model, not an accident.
  3. Prebuilt agents. Pega's agentic assignment processing and document agent ship in Infinity '26217. The bank will rebuild equivalents in Agent.CBA where needed.
  4. Pega marketing friction. Pega will keep shipping agent features, and every Pega account conversation will raise them. The COE needs a short, honest answer ready (Section 10).
The line, stated once

A Pega agent is a production agent that happens to run inside a rules engine. The bank's position is not that Pega cannot execute it. The position is that production agents are software assets, and software assets live in the bank's code, eval, and memory layers, which are in Agent.CBA.

06Target architecture: two planes and a case spine

The architecture is deliberately boring: a process plane, an agent plane, and five standard ways they talk. Anything outside the five needs a design review.

Experience and human work

Constellation applications, case worker screens, approvals, correspondence

  • Humans see proposals, evidence, and confidence. Humans decide where the rules say they must.

Pega plane: system of process and record

Case lifecycle, assignments, SLAs, decisions, integration, audit

  • Deterministic orchestration, decision logic, and the case data model.
  • The governed tool surface agents call: MCP server backed by reviewed Rule-AI-Tool definitions.
  • Evidence: case history, AI Tracer, PDC, conversation records.

Nothing in this plane plans. It executes defined steps, calls services, and records what happened.

Agent.CBA plane: system of cognition

Agent runtime, tool adapters, durable orchestration, evals, model gateway

  • Typed agents (Pydantic-style), multi-step tool use, schema-validated outputs.
  • Temporal for durable execution, retries, and human-in-the-loop waits.
  • HoneyHive for traces, datasets, and release-gate evaluations.
  • Model access through the bank gateway; provider SDKs behind interfaces.

Agents read and act on Pega only through the tool surface. No side doors into case data.

Standard interaction patterns

P1

Agent calls Pega: the MCP tool surface

Use when an Agent.CBA agent needs case context or must take an action on a case. This is the primary seam.

  1. Pega team defines the action or read as a Rule-AI-Tool, with an intent description, parameter schema, and confirmation flag as appropriate28.
  2. The tool is exposed through a Rule-Service-MCP service, scoped to the domain, with OAuth 2.0 client registration57.
  3. Agent.CBA registers the MCP endpoint and grants the agent only the tools it needs. No wildcard estates.
  4. Every call carries the agent run identifier and the case or context identifier, so traces correlate across both planes.
  5. Pega records the interaction; the agent's trace records the tool call. Both are evidence.
Pega side: Rule-AI-Tool, Rule-Service-MCP, OAuth client, audit records Agent side: MCP client, tool allowlist, correlation ID
P2

Pega calls an agent: the agent service step

Use when a case step needs an agent outcome. Preferred over A2A for first deployments; it is the least coupled option.

  1. Agent.CBA publishes a versioned service for the capability (typed request and response, schema documented).
  2. The Pega case step calls it through a standard connector. Long agent runs are scheduled asynchronously (queue or parallel run) so the case does not block a worker9.
  3. The response is mapped into case properties and passed through deterministic validation before it changes case state or triggers an action.
  4. Timeouts, retries, and fallback are defined in the case, not assumed: what happens when the agent is slow, unavailable, or returns a low-confidence result.
  5. The service call and its outcome are recorded in case history, with the agent run ID stored on the case.
Pega side: connector, service step, data transform mapping, error paths Agent side: versioned endpoint, contract tests, SLA
P3

Human in the loop: proposal, decision, feedback

Use for any material outcome. Pega's own design guidance matches this split: the agent recommends, deterministic rules decide when automation is allowed, and the case owns the human work19.

  1. The agent returns a structured proposal: recommendation, rationale, evidence, confidence, and the model and prompt version used.
  2. Pega routes the proposal as an assignment with the evidence in the UI, not in a chat transcript.
  3. The human decision is recorded against the proposal, including edits. Edited outcomes are the best eval data the bank has.
  4. Where review volume is high, sample review is defined by risk tier, not by reviewer availability59.
  5. Feedback flows back to the Agent.CBA eval datasets on a defined schedule.
Payload: recommendation, rationale, evidence, confidence, versions Rule: agent output never directly executes an irreversible action
P4

Design time: spec, build, review, verify

Use for every change. This is the agentic SDLC loop, and it is where agents are welcome inside Pega tooling.

  1. Intake produces a design artifact: a Blueprint, a spec, or a story. Business intent is captured once, in a reviewable form20.
  2. Coding agents (through Infinity Build MCP and the authoring plugins) generate rules into an isolated branch with a ChangeRequest, never to the base ruleset22.
  3. A review gate checks the change: rule warnings, security and dependency checks, test generation, and human sign-off.
  4. Verification runs measurable checks (unit tests, view parity, scenario replay) before merge.
  5. The same loop applies to Agent.CBA code, with the additional eval tiers from Section 8.
Allowed: Blueprint, Autopilot, authoring MCP plugins, coding agents Required: branch isolation, human approval, no production data in prompts
P5

Knowledge and memory: one truth per kind

Use always. Most agent failures that look like model problems are context problems: two sources of truth, stale memory, or unlabelled knowledge.

  1. Case facts live in Pega. The agent reads them through tools, never through a copied store.
  2. Agent working memory lives in Agent.CBA with a defined retention policy and an export path. It is not a system of record.
  3. Bank knowledge (policies, product documents, procedures) comes from the bank-owned knowledge service. If Knowledge Buddy is used for a Pega experience, it is registered as a content source and its embedding-model dependency is tracked24.
  4. Every retrieved passage used in a decision is recorded with its source and version, so an auditor can reconstruct the input.
Rule: no dual memory systems without a designated truth and a sync owner

07The build and no-build decision framework

Seven questions decide the plane. If any answer lands in the right column, the work goes to Agent.CBA, and the Pega work becomes the process wrapper and the tool surface.

The seven-question test
QuestionAnswer points to PegaAnswer points to Agent.CBA
1. Does it plan?It follows defined steps.It chooses its own path to a goal.
2. How long does it run?Within a case step or a scheduled service.Across minutes, hours, or days, with waits and retries.
3. Can the output be validated deterministically before action?Yes: schema, rule, or human check catches errors before consequence.No: judgment is the product, and checks can only sample it.
4. Does behavior need to change faster than a platform release?No: the logic is stable and belongs in governance.Yes: prompts, tools, and models iterate on a code cadence.
5. Is the work directing a human inside a case?Yes: guidance, forms, approvals, correspondence.No: it acts on systems or content directly.
6. Is the work process state, assignment, or evidence?Yes: this is the case's job.No: transient reasoning state only.
7. Would an auditor ask to inspect the decision logic?If the logic is a rule, keep it as a rule.If the logic is a model behavior, it needs code artifacts, evals, and a trace.

Green list: build in Pega

  • Case lifecycle, stages, steps, alternative stages, and routing.
  • Assignments, workbaskets, SLAs, urgency, escalation.
  • Decision logic: when rules, decision tables, CDH strategies where in scope.
  • Integrations: REST, Kafka, file, and service orchestration inside the case.
  • The case data model and correspondence.
  • Human screens, approvals, and the review experience for agent proposals.
  • The MCP tool surface (Rule-AI-Tool plus Rule-Service-MCP) and its access reviews.
  • Bounded LLM transforms through GenAI Connect with deterministic validation and masking.
  • AI Tracer and PDC monitoring for anything AI in the Pega plane.
  • Design-time GenAI: Blueprint, Autopilot, authoring plugins, agent-assisted rule review, test generation.

Amber list: build in Pega only with COE review

  • Knowledge Buddy as a retrieval source in a production Pega experience (content governance, embedding-model tracking, data residency).
  • MCP client wiring from Pega to any external MCP server (Rule-Connect-MCP), including Agent.CBA-hosted tool servers. Platform-team-managed connections only.
  • A2A connectivity to Agent.CBA capabilities that expose Agent Cards (Rule-Connect-Agent). Prefer P2 until the A2A contract has run in production twice.
  • Document extraction at scale through GenAI Connect; confirm volume pricing, file-type limits, and failure fallbacks14.
  • Any new Pega GenAI feature not listed in this paper. New does not mean approved; it means unreviewed.

Red list: do not build in Pega, ever, in production

  • Production Rule-AI-Agent instances of any scope (application, case type, or data).
  • Multi-agent orchestration or agent delegation inside Pega (pzAgentTools).
  • Agentic assignment processing and prebuilt Pega agents.
  • Exposing any Pega agent externally through A2A or MCP in production (there should be no production Pega agents to expose).
  • Agent memory or conversation state as a system of record for agent behavior.
  • Prompt-governed behavior that changes outcomes without a code review and an eval.
  • LLM output directly triggering irreversible actions (payments, blocks, closures, outbound contact) without deterministic validation or human approval.
  • Direct calls from Pega rules to public model provider endpoints, bypassing the bank gateway.
The default that resolves most debates

If a team is unsure, build the process in Pega and the cognition in Agent.CBA. The integration cost is one service contract and one tool surface. The cost of guessing wrong in the other direction is a runtime the bank has decided not to govern.

08Guardrails

Twelve rules. Each has a reason, an enforcement mechanism, and an owner. These are written to be auditable: an assurance reviewer should be able to test each one against evidence.

G1

Runtime boundary

Rule
No production agent runs in Pega. Production agents run in Agent.CBA. Pega hosts process, case, tool surface, and evidence.
Why
One runtime to evaluate, secure, and instrument. APRA's April 2026 letter names non-human identity, agentic workflow controls, and exit/substitution capability as explicit expectations, and a second runtime works against all three41.
Enforcement
Architecture review gate. Rule searches for production Rule-AI-Agent instances in release audits. Sandbox evidence required for any design-time use.
Owner
COE lead, with application architects accountable per app.
G2

Curated tool surface

Rule
Agents reach Pega only through reviewed MCP tools backed by Rule-AI-Tool definitions. No agent gets raw database, connector, or DX API access. Confirmation flags are set per tool risk.
Why
Tool definitions are the real permission model for agents. A curated surface limits blast radius and makes each action reviewable in one place28.
Enforcement
Tool catalogue owned by the COE. Access reviews per domain each quarter. MCP services scoped per domain, never @baseclass everything.
Owner
COE tool catalogue steward, with domain architects.
G3

Data classification and masking at egress

Rule
Classify data before it leaves Pega or Agent.CBA boundaries. Mask PII at prompt creation. The known gap on Coach and agent rules is closed by policy: no sensitive entity enters a prompt on those surfaces until the control is available and proven16.
Why
Masking before egress is the only control that does not depend on provider behavior12. PII in traces is also a retention problem, in both HoneyHive and Pega records.
Enforcement
Data classification tags on case types and tools. Masking configured and tested per integration. Trace payload reviews in the release gate.
Owner
Data governance, with app teams implementing.
G4

Identity for non-human actors

Rule
Every agent has a registered identity, distinct from human operators and service accounts, with least-privilege tool scope. Agent identity is revocable and monitored.
Why
APRA observed that identity and access management has not adjusted to non-human actors41. MCP exposure without distinct agent identity collapses the audit question of "who acted."
Enforcement
Platform identity process for agents. OAuth client registrations per MCP service, bound to the agent identity. Quarterly access review.
Owner
Security and platform engineering, jointly.
G5

Observability and cross-plane correlation

Rule
Every agent run that touches a case carries one correlation identifier across both planes: the case ID on the agent trace, the agent run ID on the case. Pega-side AI interactions are traced in AI Tracer; agent traces land in HoneyHive.
Why
Without a shared key, incident response is manual archaeology across two tools1156. Regulators ask one question: show the sequence.
Enforcement
Contract requirement on both sides. Trace header standard in the integration template. Quarterly incident-drill test of the correlation path.
Owner
Agent.CBA platform team and Pega COE jointly.
G6

Evaluation gates before production, and after

Rule
No agent reaches production without passing the eval tiers: deterministic checks and contract tests first, judge-based quality gates second, and production monitoring with sampled scoring third. Passing evals is necessary, not sufficient: consequence-level review by risk tier still applies59.
Why
Industry survey data shows most organisations running pre-deployment evals have still had customer-facing failures after passing them59. Evals reduce risk; they do not certify.
Enforcement
Release gate in the Agent.CBA pipeline. Datasets versioned from production traces. Human review tiers defined per agent risk class.
Owner
Agent.CBA platform team, with model risk sign-off.
G7

Cost governance

Rule
Every agent has a cost budget and request, tool-call, and step limits set at the framework level, not left to prompts to respect. Runaway loops are a governed failure mode, not a billing surprise.
Why
Unbounded agent loops are the most common production cost failure in these frameworks5354. APRA's letter pairs cost discipline with control expectations for autonomous workflows41.
Enforcement
Framework budgets and limits configured per agent. Cost per run visible in traces. Budget breach alerts to the owning team. Finance review for new agent types.
Owner
Agent.CBA platform team, with product owners.
G8

Change control and versioning

Rule
Agent changes (prompts, tools, models, guardrails) are code-reviewed, versioned artifacts. Production runs pin versions. Rollback is a tested path. Pega rule changes follow the ChangeRequest and branch process.
Why
Unversioned prompt edits make every incident unreproducible. Durable workflow engines require explicit version discipline for safe deploys55.
Enforcement
Repository policy and CI checks in Agent.CBA. ChangeRequest discipline in Pega. No manual prompt edits in production, from either side.
Owner
Agent.CBA platform team and Pega COE.
G9

Human oversight proportional to consequence

Rule
Agent outputs that can harm a customer (credit decisions, blocks, closures, outbound contact) require human approval or a deterministic rule gate with documented thresholds. Confidence scores do not substitute for authority. Accountable owners are named in the register.
Why
Pega's own HITL doctrine matches this: agent recommends, rules decide, case owns human work19. The APRA letter and the Voluntary AI Safety Standard both anchor oversight to a competent, authorized, named person4148.
Enforcement
Risk-tier matrix per agent. Approval paths encoded as case assignments. Sampling schedules monitored.
Owner
Risk and compliance, with product owners.
G10

Failure handling and kill switches

Rule
Every agent integration defines timeout, retry, fallback, and containment. Agent failure must not silently degrade to a generic success path. A kill switch per agent and per tool surface exists and is tested.
Why
Silent fallbacks hide failure until it compounds. APRA expects credible fallback processes where AI supports critical operations41.
Enforcement
Failure-mode section in every design review. Kill-switch test in the pre-production checklist. Dead-letter queues for failed agent tasks.
Owner
Application teams with platform support.
G11

Portability and exit

Rule
Agent logic lives in the Agent.CBA repository. Prompts, tool schemas, eval datasets, and memory schemas are bank-owned artifacts. For Pega-side AI: model routes point at the bank gateway, and no runtime agent artifacts are created in Pega. Each agent family has a named exit test run annually.
Why
Memory and prompt logic are the least portable assets in an agent estate; most large enterprises cannot yet produce owner, scope, cost, and approver per production agent on demand50. CPS 230 makes substitution and exit planning a supervisory expectation for critical providers43.
Enforcement
Exit test in the agent register. Annual portability review. Model route inventory through the gateway, not direct endpoints.
Owner
Architecture, with Agent.CBA platform team.
G12

Regulatory mapping stays current

Rule
Agent designs map to the four APRA observation areas (security, governance, supplier and concentration, assurance), CPS 230/234 obligations, the Voluntary AI Safety Standard guardrails, and the automated decision-making disclosure rules that commence 10 December 2026414344454648.
Why
APP 1.7-1.9 captures decision-support tools, not only fully automated decisions, and human review does not remove a tool from scope46. ASIC's banking AI review starts in 2026-2747.
Enforcement
Regulatory mapping section in each agent design. Privacy policy disclosure updates tracked by Legal. Quarter-end obligations review with Risk.
Owner
Compliance and legal, with COE support.

09Design-time governance: the developer agentic loop

Design time is where Pega's agentic features earn their place. The runtime ban does not apply to tools that write, review, and verify code, provided the guardrails below hold.

The loop

  1. Intake. A story or a Blueprint captures intent once. Blueprint is free to use, generates user stories on import, and its data handling is documented by Pega (anonymized process descriptions only, no client data to model subproviders)20. Data residency caveat: Blueprint regions exist for UK/EU storage, but cross-region blueprints remain in US-East; confirm the bank's approved region before any sensitive content is entered20.
  2. Design. Autopilot and the Blueprint assistant scaffold data types, views, and case structure. Rules: Autopilot cannot modify existing case types or data objects, so teams pick one path per object and stick to it; parallel branch use can generate duplicate rules, so one owner per branch21.
  3. Build. Coding agents connect through the authoring MCP plugins and write rules into an isolated branch under a ChangeRequest. The plugin setup validates connectivity and write access before work begins22.
  4. Review. Rule warnings, dependency checks, and an AI review gate run on the change. Findings are severity-ranked; humans read the summary and the flagged items, not the whole diff.
  5. Verify. PegaUnit and scenario tests run before merge. Generated tests are reviewed like generated code: existence is not evidence of coverage.
  6. Approve. A human owner approves the merge. The agent never merges its own change. This mirrors the bank's existing release gate: review, human eyes, then the merge.

12Failure modes of this position, and triggers to revisit

A policy that cannot name its own failure modes is a slogan. These are the ways this split breaks, and the conditions that would change the position.

Ways this position breaks

  1. Two-plane drift. The tool surface stagnates while agents evolve, so agents operate on stale context and teams route around Pega. Mitigation: tool catalogue ownership, quarterly surface reviews, and fast turnaround on tool requests.
  2. Taxonomy erosion. Under delivery pressure, "it's just a small agent" enters Pega runtime quietly. Mitigation: automated rule searches, environment controls, and a visible exception process rather than a hidden one.
  3. Integration tax. Every agent needs Pega context, and the tool surface is not rich enough, so each team builds its own bridge. Mitigation: invest in reference tool sets per domain before teams ask.
  4. Skill split. Pega developers and agent engineers drift apart, and handoffs become the bottleneck. Mitigation: shared design reviews, a common pattern library, and rotation between the two groups.
  5. Vendor pressure. Pega ships an agent capability the business genuinely wants (for example, a deep case-context agent that would cost a year to rebuild). Mitigation: a working waiver path with exit tests, not a blanket refusal.
  6. Regulatory spread. Two runtimes mean two mappings to APRA's observation areas. Mitigation: one register, one control library, one incident playbook spanning both planes (G12).

Triggers to revisit this position

The COE will formally reassess if any of the following occurs:

  • Pega ships portability for agent artifacts: agent definitions, prompts, and eval-relevant metadata exportable as code or open format, with memory export.
  • Agent.CBA cannot provide case-context tools at the depth Pega applications need, and the gap persists beyond two quarters.
  • Pega's runtime gains bank-approved eval parity: a supported way to run the bank's evaluation suite against Pega-hosted agents and produce equivalent evidence.
  • The bank adopts a multi-runtime agent policy, or Pega's MCP surface becomes the only integration seam for a class of use cases where placing the agent in Pega is materially cheaper.
  • A regulator or auditor explicitly requires agent execution in the system of record, changing the assurance calculus.

Until then, the position stands: design time in Pega, runtime in Agent.CBA, the case in the middle, the tool surface as the seam.

ACapability detail and verified mechanics

This appendix records the technical specifics behind Section 5. Field names and structures marked "verified live" were read from the authoring skill payloads in our Pega MCP environment during preparation of this paper2728.

A.1 Agent rule structure (Rule-AI-Agent, Infinity 25+, 08-25-01+)

  • Identity: pxObjClass = Rule-AI-Agent; applies-to class in pyClassName; pyPurpose as the agent identifier; scope in pyAgentScope (Other, Application, CaseType, Data). Modern schema is pyVersionNumber: v2.
  • Model binding: pyGenAIConfig plus pyModelConfiguration with pyModelId, pyProvider (hosting backend such as bedrock, azure, vertex), pyModelName, and pyCreator (model maker). Model metadata must be read live from D_pxAIModelsForCoachOrAgent, not hard-coded27.
  • Behavior: pyGenAIDef with pySystemPrompt, pyGuardrailsPrompt, pyResponseStylePrompt, and pyExamples.
  • Tool and knowledge lists: pzActionTools, pzKnowledgeTools, pzAgentTools, pzCaseTypeTools, pzExternalAgents (Rule-Connect-Agent), pzMCPClients (Rule-Connect-MCP), and pzAIDataSources (preloaded data pages; higher token cost than on-demand knowledge tools).
  • Guardrails are a distinct prompt-class field on the agent rule, separate from the system prompt, confirmed by Pega's own Agent Inspector utility23.

A.2 Tool definitions (Rule-AI-Tool)

  • Core fields: pyPurpose (tool name agents call), pyIntentDescription (natural-language instructions for the model), pyIntentActionPage (the backing rule), pyAskConfirmation and pyAskConfirmationMessage (confirmation gate), and pyRetentionPolicy (ALWAYS_RETAIN, RETAIN_UNTIL_ACTIONED, EPHEMERAL)28.
  • Backing categories: activity, data page, flow action, case type, section, buddy, and agent. Case type and section categories are relevant for tool surfaces; agent-backed tools are not permitted in our production pattern.
  • Parameter conventions differ between the tool interface and the backing rule (pyParametersParamReq values -1/0 versus pyRequired true/false), a common source of broken tools. The COE tool clinic exists because of this.
  • A tool referencing a non-existent backing rule fails at runtime. Backing rules are validated before the tool is created28.

A.3 MCP server (Rule-Service-MCP)

  • Native in Infinity '26. Created under Records, Integration Services, Service MCP. Exposes case types, workflows, automations, data pages, and agents as MCP tools57.
  • Service identity: pyClassName plus pyServiceName. Protocol version in pyMCPVersion. Enabled state in pyIsMCPServiceEnabled. Tools are referenced in pzMCPTools (non-case-type) and pzCaseTypeTools (case-type), each entry pointing at an existing Rule-AI-Tool by rule name28.
  • Auth: OAuth 2.0 client registration; external clients connect with an authorization-code handshake. Pega positions MCP as another channel that keeps existing application policies6.
  • Known constraints: UI Kit parameter mapping for case-type tools has practitioner-reported gaps; Constellation works with tool parameters mapping to case properties; the OOTB pxCommon service may need views per assignment in UI Kit applications6.

A.4 MCP client and A2A

  • Rule-Connect-MCP (MCP Connect) arrived in Platform 25.1.3. Default transport is streamable HTTP. In 25.1.3, configuration required Dev Studio because the Advanced Tools tab was not available in App Studio9.
  • Rule-Connect-Agent supports Protocol = Agent2Agent. The Agent Card URL must resolve to the well-known agent card path; a missing or malformed card produces connector errors that look unrelated to the card8. Pega's Inspector supports A2A v0.3 over JSON-RPC 2.0 via .well-known/agent.json23.
  • Practitioner-reported failure modes: HTTP 422 from contract mismatches, "Service URL was not provided" when the card path was wrong, and GET health checks passing while POST invocation never occurs8.

A.5 Audit, observability, and model governance

  • Conversation and execution records: Pega-Autopilot-Conversation class, PXCONV- instances, with pyContextID linking a run to its case. Reported by Pega staff on the community forum; confirm object retention rules with the platform team10.
  • AI Tracer exposes reasoning steps, tool calls with inputs and outputs, latency per step, and token counts per agent, tool call, and data retrieval11.
  • PDC raises alerts when a model approaches deprecation (PEGA0175) or is no longer available (PEGA0176). The Model Availability Dashboard tracks feature mapping, region, and lifecycle status per model13.
  • Runtime content filtering covers six categories across supported providers, including prompt injection and malicious URIs, applied to prompts and responses. Provider confidence thresholds vary; that limit is Pega's own published caveat12.

A.6 Design-time specifics

  • Blueprint imports can auto-generate AI Agents since '25, which is exactly the artifact class this paper keeps out of production; treat generated agents as prototypes20.
  • Autopilot constraints: creates new objects only, cannot modify existing case types or data objects; regeneration reported as ineffective in an independent project review; picklist properties were initially created as text in that review21.
  • Authoring plugins support Claude Code, GitHub Copilot CLI, Codex, Devin, and opencode, with a setup skill that verifies connectivity and write access and stores configuration outside the repo22.

EGlossary

Agent (in this paper)
An LLM-driven software component that decides which actions to take over multiple steps toward a goal, choosing tools at runtime.
Agent.CBA
The bank's production runtime for AI agents (internal brief). Python-based, with typed agents, durable orchestration, evaluation, and observability tooling. Not publicly branded.
Assistive AI
A single-turn or single-task model use that produces a draft, summary, or suggestion for a human or rule to act on.
ChangeRequest
Pega's change management case that isolates rule changes on a branch for review and approval.
Eval (evaluation)
A scored test of agent behavior, run against versioned datasets before release and sampled in production. Deterministic checks and judge-based scoring are both evals.
HITL (human in the loop)
A design where a human reviews or approves an agent proposal before the outcome takes effect.
MCP (Model Context Protocol)
An open protocol for tool discovery and invocation by AI clients. Pega exposes capabilities as MCP tools and can also consume external MCP servers.
PXCONV
Instance prefix for Pega's persisted agent conversation records (class Pega-Autopilot-Conversation), per Pega staff reporting.
Rule-AI-Agent
Pega's agent rule type (Infinity 25+). The artifact this paper keeps out of production.
Rule-AI-Tool
Pega's tool definition rule. The unit of the governed tool surface agents call.
Rule-Service-MCP
Pega's MCP server rule (Infinity '26) that publishes case types and tools to MCP clients.
Tool surface
The curated set of actions and reads exposed to agents, each defined as a reviewed tool with least privilege.
Two planes
The process plane (Pega) and the agent plane (Agent.CBA), joined by the case spine and the tool surface.
